# 🎫 演劇公演 チケット販売管理システム 要件定義書（v1.1）

> このページは、小劇場の演劇公演向けチケット販売管理システムの要件を整理したものです。既存の他社チケットシステムを実運用した経験から得られたペインを解決することを目的とし、別途開発中の「事前物販OS」「当日物販管理アプリ」との連携（ギャランティ合算）を前提とします。
>
> 作成日: 2026-07-26 ／ 更新日: 2026-07-26（ヒアリング回答を反映し主要論点を確定） ／ ステータス: 一次確定版

# 1. 背景と目的

小劇場の演劇公演では、チケット販売が単なる座席の販売ではなく、**キャストごとの「扱い」＝ギャランティに直結する営業活動の基盤**になっている。しかし既存のチケットシステムは大劇場・一般興行向けの設計が中心で、小劇場特有の運用（指定席と自由席の混合販売、キャスト扱いの管理、キャスト個別予約の吸収）に対応できていない。

本システムは、以下を実現する小劇場特化のチケット販売管理システムを構築する。

- 指定席（ロイヤルカスタマー向け高単価前方席）と自由席（一般席）の**混合販売**
- 劇場ごと・公演ごとに異なる**柔軟な座席レイアウト作成**
- キャストごとの**「扱い」管理とギャランティ連動**
- キャストが**自身の扱いの売上をリアルタイムに把握**できるダッシュボード（オンライン決済対応）
- キャストが親族・友人向けに行う**個別予約（当日現金・キャスト代払い含む）のシステム内管理**
- 物販システム（事前・当日・後日）との**売上合算によるギャランティの統合把握**

将来的には自劇団だけでなく**他劇団への提供**も視野に入れ、物販システム群と同様に拡張性（マルチテナント）を重視した設計とする。外部プレイガイド（こりっち等）との**併売は行わず**、チケット販売は本システムに一本化する。

# 2. 解決すべきペインと解決方針

| # | 既存システムのペイン | 本システムの解決方針 |
|---|---|---|
| P1 | ロイヤルカスタマー向け高単価の前方席は座席指定で売りたいが、一般席は自由席で売りたい。両者を混合で販売できるシステムがほぼない | 1公演内で**指定席エリアと自由席エリアを併存**させる席種設計。指定席は座席単位、自由席は枚数（キャパシティ）単位で在庫管理する |
| P2 | 同じ劇場でも席の作り方（組み方）で座席数・配置が公演ごとに異なる | **会場レイアウトをテンプレート化しつつ、公演ごとに座席の増減・配置変更・エリア割りを編集**できる座席レイアウトビルダーを持つ |
| P3 | 販売時にキャストごとの「扱い」を定義する必要があり、ギャランティに直結するが、既存システムに概念がない | チケット購入・予約に**「扱い」を属性として持たせ**、扱い別の売上集計とギャランティ計算ルール（スナップショット保存）を標準機能にする |
| P4 | キャストが自身の売上をリアルタイムに把握できるのは「こりっち」のみ。しかし「こりっち」は予約のみでオンライン決済非対応 → 未来場リスク | **オンライン決済（事前決済）を標準**とし、キャスト本人が自分の扱い分の売上・来場状況を**リアルタイムに閲覧**できるダッシュボードを提供する |
| P5 | キャストによる親族・友人向け個別予約（当日現金払い・キャスト代払い等）が主催とキャストのLINE個別やり取りで管理され、一般販売と不整合・トラブルが多発 | キャスト自身がシステム上で**個別予約（ゲスト予約）を起票**できる機能を提供。一般販売と**同一の座席・在庫プールで管理**し、支払方法（オンライン／当日現金／キャスト代払い）を選択できる |
| P6 | ギャランティはチケット＋事前物販＋当日物販＋後日物販の合算だが、統合してリアルタイムに確認する手段がない | **物販システム群（事前物販OS・当日物販アプリ）と同一Supabase基盤で連携**し、キャスト・主催が「チケット＋物販」の合算売上・ギャランティ見込みを相互にリアルタイム確認できるようにする |

# 3. 対象ユーザーとロール

物販システム群と共通の Supabase Auth・ロール体系に揃える（org 単位のマルチテナント前提）。

- **主催／管理者（Admin）**: 公演・座席レイアウト・券種・扱い・ギャランティルールの管理。全キャストの売上・予約・来場状況を閲覧可能。当日現金の精算管理。
- **制作／スタッフ（Staff）**: 受付業務（チェックイン・当日精算・当日券販売）を行う。**キャスト別の売上・ギャランティ集計は閲覧不可**（物販側の情報分離方針と一貫）。
- **キャスト（Cast）**: 自分の扱いの売上・予約状況・来場状況・ギャランティ見込み（チケット＋物販合算）のみ閲覧可能。自分のゲスト予約の起票・キャンセルが可能。**他キャストの情報は一切閲覧不可（厳密分離）**。
- **購入者（一般顧客）**: アカウント登録なし（または軽量な購入者情報のみ）でチケット購入できる。座席選択（指定席）・扱い選択・オンライン決済・電子チケット受け取り・同伴者へのチケット分配。

## 3.1 情報分離要件（物販システムと共通方針）

- Supabase **Row Level Security (RLS)** により DB 層でロール別アクセス制御を強制する（キャストは自分の扱い分のみ、スタッフはキャスト別集計にアクセス不可）。
- フロント側フィルタに依存せず、API レスポンス・DOM レベルでも閲覧権限外のデータを保持しない。
- 全エンティティに **org_id** を持たせ、RLS も org_id で分離する（他劇団提供を見据えた両システム共通方針）。

# 4. 主要概念・用語の整理

| 用語 | 定義 |
|---|---|
| 公演（event） | 1つの演劇公演。複数ステージ（回）を内包する。物販システムと ID 体系を揃える |
| ステージ（stage） | 公演内の1回の上演（昼の部・夜の部等）。チケットはステージ単位で販売する |
| 座席レイアウト（seat layout） | 会場にどう座席を組むかの定義。会場テンプレートから公演ごとに派生・編集する |
| 席種（seat class） | 指定席／自由席の区分＋価格帯（例: プレミアム指定席 8,000円、一般自由席 4,500円） |
| 券種（ticket type） | 販売単位（一般前売・当日券・学割等）。席種 × 販売条件の組み合わせ |
| 扱い | そのチケットがどのキャストの営業成果として計上されるかの区分。ギャランティ計算の基礎。購入時は**「一般」（＝主催扱い）または各キャスト名から必ず選択**する |
| ゲスト予約 | キャストが親族・友人等のために起票する個別予約。一般販売と同一在庫を消費する |
| 分配 | 複数枚購入したチケットの一部を同伴者（第三者）に譲渡すること。全枚数の譲渡は不可 |
| ギャランティ（ギャラ） | キャストへの報酬。チケット扱い売上＋物販（事前・当日・後日）売上の合算に対して、キャストごとのルールで算出する |

# 5. 機能要件

## 5.1 公演・ステージ管理（主催）

- 公演の作成・編集（公演名・期間・会場・告知情報）
- ステージ（回）の作成・編集（日時・開場/開演時間）
- ステージごとの販売スケジュール設定（販売開始・終了日時、先行/一般の販売期間）
- 公演・キャストのマスタは物販システム群と ID 体系を統一する（突合不能を防ぐ）

## 5.2 座席レイアウト管理（ペイン P2）

- **会場テンプレート**: 会場（劇場）ごとに基本レイアウト（列・番号・ブロック構成）を登録できる
- **公演別レイアウト**: テンプレートから複製し、公演ごとに座席の追加・削除・配置変更ができる（同じ劇場でも公演ごとの席の組み方の違いを吸収）
- **エリア（ブロック）定義**: レイアウト上の座席群をエリアにまとめ、席種（指定席/自由席）と価格を割り当てる
- 自由席エリアは座席単位の管理を行わず、**エリアごとのキャパシティ（販売可能枚数）**のみ設定する
- 桟敷・増席・見切れ席など小劇場特有の変則配置に対応できる（座席のグリッドに縛られない自由配置）
- 販売開始後のレイアウト変更（増席等）にも対応する（既販売座席の整合を保護した上での追加・変更）

## 5.3 席種・券種・混合販売（ペイン P1）

- 1ステージ内で**指定席と自由席を併存**して販売できる
  - 指定席: 座席単位で在庫管理。購入時に座席を確定する
  - 自由席: 枚数単位で在庫管理。**整理番号を購入順で発番する（確定）**
- 席種ごとに価格を設定できる（高単価前方指定席＋一般自由席の構成を標準ユースケースとする）
- 券種（一般前売・当日券・学割・招待等）を席種に紐づけて定義できる
- 招待・関係者枠は在庫から事前に確保（ホールド）できる

## 5.4 一般販売・購入フロー（ペイン P4）

- 公演ごとの**オンライン販売ページ**を自動生成する（スマホ最適化）
- 購入フロー: ステージ選択 → 席種選択 →（指定席の場合）座席選択 → **扱い選択** → 購入者情報入力 → オンライン決済 → 電子チケット発行
- **指定席の座席選択は2方式の両対応（確定）**:
  1. 購入者が座席図から自分で選ぶ
  2. おまかせ（先着で空き席から自動割当）
- **扱い選択（確定）**: 選択肢は**「一般」（＝主催扱い）＋各キャスト名**とし、購入者は必ずいずれかを選択する。キャストからの案内リンク（キャスト個別URL）経由の場合は該当キャストを自動で設定する
- **オンライン決済**: Stripe による事前決済を標準とする（物販システム群と決済基盤を揃える）
- 決済完了と同時に座席・在庫を確定し、**予約のみの未決済枠が残らない**ことを原則とする（未来場リスクの排除）
- 電子チケット（QRコード）を発行する。QRの提示手段は2系統（確定）:
  1. **開演1時間前に来場者へメールでQRを送付**する
  2. 購入者向けチケットページ（サイト上）でいつでもQRを表示できる
- 購入完了メール・リマインドメールを自動送信する
- 座席選択中の仮押さえ（一定時間のロック）と、決済未完了時の自動解放を行う

## 5.5 キャスト扱い管理・ギャランティ連動（ペイン P3）

- 公演ごとにキャストを登録し、キャストごとの**扱い定義**を設定できる
  - ギャランティ計算ルール: 定率（扱い売上の◯%）／定額（1枚あたり◯円）／ノルマ方式（◯枚までは対象外、超過分に◯円）等、キャストごとに個別設定
  - 対象範囲: チケット扱い売上に適用。**最終的なギャランティは物販売上と合算して算出**する（5.9）
- 販売トランザクションには、適用した**単価・率・ルールのスナップショット**を保存し、後からルールを変更しても過去の計算が再現できるようにする（物販システムと共通の設計原則）
- 「一般」扱いで売れた分はキャストのギャランティ対象外（主催の売上）とする
- 扱いの付け替え（購入後の扱い変更）は主催のみが行え、変更履歴を残す

## 5.6 キャストダッシュボード（ペイン P4）

- キャスト本人が**自分の扱い分のみ**をリアルタイムに閲覧できる
  - ステージ別・券種別の販売枚数・売上金額
  - ゲスト予約の状況（未決済・入金済み・来場済み）
  - 来場状況（チェックイン済み枚数）
  - **ギャランティ見込み（チケット＋物販合算）** ← 事前物販OSが集計した合算値を参照表示（5.9）
- キャスト個別の**案内用URL／QR**を発行できる（このリンク経由の購入は自動的に本人扱いになる）。SNS・LINEでの営業活動にそのまま使えることを重視する
- 「まだ買っていない既存顧客へのアプローチ」を支援するため、過去公演の自分扱い購入者リスト（本人の扱い分のみ）の閲覧可否を論点として検討する（個人情報の扱いに注意）

## 5.7 キャストゲスト予約（ペイン P5）

キャストが親族・友人等のために行う個別予約を、LINE 等の口頭運用からシステムに移す。

- キャストが自分のダッシュボードから**ゲスト予約を起票**できる（ゲスト氏名・枚数・ステージ・席種）
- **起票で即確定**とし、主催の承認は不要（確定）。**キャスト自身でキャンセルも可能**とする
- ゲスト予約も**一般販売と同一の座席・在庫プールを消費**する（不整合・ダブルブッキングの根絶）
- **指定席の座席割当は空き席からの自動割当（確定）**:
  - 複数名分の予約の場合は**横並びで連番となる席**を優先して割り当てる
  - 該当する連番席がない場合は、**キャストに「予約を断念する」か「離れ席でも予約する」かを確認**した上で確定する
- **支払方法を予約ごとに選択**できる:
  1. **オンライン決済**: ゲストに決済リンクを送付し、ゲスト自身が Stripe で支払う（期限内未決済は自動キャンセル）
  2. **当日現金**: ゲストが当日受付で支払う。受付画面で「未収」として表示され、受付時に収受を記録する
  3. **キャスト代払い**: キャストが代理で支払う。**精算方法は次の3つから選択（確定）**: (a) キャストがオンライン決済（Stripe）、(b) 当日受付での現金精算、(c) 主催とキャスト間の現金精算（立替として記録し、後日精算）
- 主催はゲスト予約の一覧（全キャスト分）と支払状況を一元的に把握できる。キャストは自分の起票分のみ閲覧できる
- 予約の起票・変更・キャンセルの操作履歴を残す

## 5.8 当日受付・来場管理

- **チェックインは購入者側がQRを提示する形式（確定）**。受付スタッフがスマホ/タブレット（本システムのPWA）で読み取る
  - QRは開演1時間前の自動メール送付＋購入者向けチケットページでの常時表示の2系統で提供（5.4）
- 自由席は購入順の整理番号による入場順管理に対応
- **当日現金予約の収受**: 未収のゲスト予約を受付画面で照会し、現金収受を記録して入場させる
- 当日券販売（現金／QR決済）: 残在庫の範囲で受付にて販売できる
- 来場状況のリアルタイム表示（主催: 全体、キャスト: 自分の扱い分）
- 受付の現金授受は公演単位で締め・照合できる（当日物販アプリのレジ締めと同様の考え方）
- **受付は本システムの PWA で行い、当日物販アプリとは分離する（確定・堅牢性判断）**:
  - チケット受付と物販レジは障害が相互に波及しない独立系統とする。当日物販アプリ（Flutter・オフラインファースト）にチケット機能を同居させると複雑性・障害リスクが増すため
  - 受付端末はオンライン照合を基本とする。QRトークンは署名付きのため、通信断時も**署名検証による真正性確認は可能**（使用済み判定はオンライン復帰後に整合）。加えて紙の予約リスト出力（CSV/印刷用）を障害時フォールバックとして用意する
  - 動員数の物販側への連携は疎結合の参考値連携に留める（5.9）

## 5.9 物販システム連携・ギャランティ合算（ペイン P6）

別途開発中の物販システム群と連携し、ギャランティを統合管理する。

- **連携先**:
  - 事前物販OS（Next.js / Supabase / Stripe。マスタの正。**後日物販もここで扱う（確定）**）
  - 当日物販管理アプリ（Flutter / Supabase。当日レジ・在庫）
- **連携方針**（当日物販アプリ要件定義書 10章の方針と整合）:
  - **同一 Supabase プロジェクトを共有**し、Auth を共通化する
  - 公演・キャスト・組織（org）の **ID 体系を統一**する（独自採番しない）
- **ギャランティ合算の集約先（確定・堅牢性判断）**: **事前物販OS側に一本化**する
  - 物販側要件で「キックバック最終合算は事前物販OS側」「キャスト閲覧は事前OS側に集約」と確定済みであり、合算ロジックを二重実装しない（計算結果の不一致リスクを排除）
  - チケットシステムは**チケット領域のデータの正**として、扱い別チケット売上（純額・ギャランティスナップショット付き）を提供する
  - 本システムのキャストダッシュボードでは、チケット領域の詳細＋事前物販OSが算出した合算サマリを参照表示する
- **データ提供形式（確定・堅牢性判断）**: 同一Supabase内に、チケットシステムが所有する**読み取り専用の集計ビュー（契約スキーマ）**を公開し、事前物販OSはそのビューのみを参照する
  - 内部テーブルへの直接参照は禁止し、スキーマ変更の影響を遮断する（物販側 12.5「経路の役割分担」と同じ設計原則）
  - ビューの列構成を契約として固定し、将来システムを分離する場合はそのまま API 化できる形にする
- **動員数連携**: 物販側ダッシュボードへ公演・ステージごとの動員数・チケット販売数を参考値として提供する（同じ契約ビュー経由）
- 連携が取れない場合でもチケットシステム単体で販売・受付運用が完結する（疎結合フォールバック）

## 5.10 キャンセル・払い戻し・変更

- **購入者都合キャンセル（確定）**: 可能とし、**キャンセル手数料として販売額の5%＋Stripe決済手数料**を購入者負担とする（返金額 ＝ 支払額 − Stripe手数料 − 販売額の5%）
- キャンセル期限は公演・券種ごとに設定できる
- 公演中止・延期時の一括払い戻し（Stripe 返金連携。この場合の手数料負担は主催側ポリシーで設定）
- 座席・ステージの変更（主催操作。履歴を残す）
- 払い戻し・取消はギャランティ計算に連動して差し引く（純額ベースで算出。物販側 12.1 と同方針）
- **リセール（有償転売）には対応しない（確定）**。行きたい人が行けなくなった場合はキャンセル→在庫戻し→再販で対応する

## 5.11 チケット分配（同伴者への譲渡）

- **複数枚購入したチケットの一部を第三者（同伴者）に譲渡できる（確定）**。例: 2枚購入のうち1枚を友人に分配する
- **全枚数の譲渡は不可**: 購入者は最低1枚を自分の手元に残す
- 分配は分配リンク（またはQR）の送付で行い、受け取った側は自分のスマホで自分のQRチケットを表示できる（アカウント登録不要）
- 分配されたチケットのチェックイン・扱い集計・ギャランティ計算は元の注文に紐づいたまま変わらない
- 分配の取り消し（未チェックインの場合のみ）に対応する

## 5.12 集計・帳票

- 主催向けダッシュボード: 全体売上／ステージ別／席種・券種別／扱い（キャスト）別／販売チャネル別（一般・ゲスト予約・当日券）／決済手段別
- 販売・来場・ギャランティの CSV エクスポート（公演後の精算用）
- 受付用の予約リスト出力（紙フォールバック用。5.8）

# 6. 非機能要件

- **決済の確実性**: 決済と在庫確定の整合（二重販売・取りこぼしの防止）。Stripe Webhook の冪等処理
- **在庫の一貫性**: 指定席の同時購入競合を排他制御で防ぐ（仮押さえ→確定のロック設計）。自由席はキャパシティの原子的な減算と購入順の整理番号発番
- **計算の再現性**: ギャランティ計算は適用ルールのスナップショットをトランザクションに保持し、後からルールを変えても過去の計算が再現できる
- **権限のDB層強制**: RLS によるキャスト間情報分離・スタッフのキャスト別集計非表示・org_id 分離
- **連携の契約化**: 物販システムへのデータ提供は読み取り専用の契約ビューに限定し、内部スキーマ変更の影響を遮断する
- **拡張性**: マルチテナント（org 階層）を最初から持つ。全エンティティに org_id
- **可用性**: 販売開始直後のアクセススパイク（人気公演の張り付き）に耐える
- **個人情報保護**: 購入者情報（氏名・メール等）の適切な管理。キャストに開示する購入者情報の範囲を最小化する

# 8. 技術スタック（想定）

物販システム群との整合を最優先する。

- **フロントエンド**: Next.js（購入者向け販売ページ／主催・キャスト・受付の各ダッシュボード）。事前物販OSとブランド・トーンを揃える
- **バックエンド / DB**: **Supabase（PostgreSQL + RLS）**。物販システム群と**同一プロジェクトを共有**
- **認証**: Supabase Auth（物販システムと共通。admin / staff / cast ロール）。購入者は原則アカウントレス
- **決済**: **Stripe**（Checkout / Payment Links / Webhook。事前物販OSと共通基盤）
- **電子チケット**: 署名付き QR トークン（物販側の引き換えQR・領収書トークンと同様に HMAC 署名。鍵は用途別に分離）。開演1時間前のメール送付＋サイト上表示の2系統で提供
- **メール送信**: 購入完了・決済リンク・QR送付（開演1時間前）・リマインドの自動送信
- **受付端末**: スマホ/タブレットのブラウザ（**PWA**）。当日物販アプリとは分離した独立系統とする（5.8）

# 9. MVP（最初に作るもの）の提案

拡張性は意識しつつ、ペインの中核（P1〜P5）を最短で解決する構成を優先する。

1. 単一劇団・単一組織前提（org_id は最初から持つ）
2. 公演・ステージ・座席レイアウト作成（テンプレ複製＋編集、指定席／自由席エリア）
3. 指定席＋自由席の混合オンライン販売（座席図選択／おまかせ自動割当・Stripe 決済・電子チケット発行）
4. 扱い選択（「一般」＋各キャスト・キャスト個別URL）と扱い別集計
5. キャストダッシュボード（自分の扱い分のリアルタイム売上・RLS 分離）
6. キャストゲスト予約（即確定・座席自動割当・オンライン決済リンク／当日現金／キャスト代払い3方式精算）
7. 当日受付: 購入者提示QRのチェックイン＋当日現金収受の記録＋紙リスト出力
8. チケット分配（複数枚購入時の同伴者への譲渡。全譲渡は不可）
9. 購入者都合キャンセル（5%＋Stripe手数料）と在庫戻し
10. 主催ダッシュボード＋CSV エクスポート
11. ギャランティルール設定・スナップショット保存＋事前物販OS向け契約ビューの公開
12. 自由席整理番号の購入順発番と開演1時間前QRメール送付

**Phase 2 以降**: 事前物販OS側でのギャランティ合算表示との接続（事前物販OS側の実装進捗に依存）、過去公演顧客リストによる営業支援、リマインドメールの高度化、マルチテナント公開（他劇団提供・手数料5%モデル）、受付の障害時運用ツール強化。

# 10. 確定事項（2026-07-26 ヒアリング結果）

| 論点 | 決定事項 |
|---|---|
| 扱い選択の必須性 | **「一般」という名称で主催扱いを選択肢に含め、必須選択**とする。キャスト選択も可能 |
| 指定席の座席選択方式 | **両対応**（購入者が座席図から選ぶ／先着自動割当） |
| 自由席の整理番号 | **発番する。購入順** |
| ゲスト予約の承認フロー | **キャスト起票で即確定。キャストからキャンセル可能**。座席は空き席から**自動割当**（複数名分は横並び連番席を優先。連番席がない場合はキャストに「断念」か「離れ席で予約」かを確認） |
| キャスト代払いの精算方法 | **3方式から選択**: 当日現金精算／キャストがオンライン決済／主催とキャストの現金精算（立替記録） |
| キャンセルポリシー | 購入者都合キャンセルは**Stripe手数料と別に販売額の5%**を手数料とする |
| ギャランティ合算の集約先 | **事前物販OS側に一本化**（堅牢性判断: 合算ロジックの二重実装を避ける）。データ提供は**チケットシステム所有の読み取り専用契約ビュー**経由（内部テーブル直接参照禁止。将来のAPI化に対応できる形） |
| 外部プレイガイド併売 | **併売しない**（本システムに一本化） |
| 受付のオフライン耐性 | **購入者側がQRを提示する形式**とし、開演1時間前のメール送付＋サイト上表示でQRを提供。受付はオンライン照合基本＋署名検証・紙リストのフォールバック |
| 当日物販アプリとの受付統合 | **本システムの PWA で受付を行い、当日物販アプリとは分離**（堅牢性判断: 障害の相互波及を防ぐ独立系統） |
| 後日物販の扱い | **事前物販OSで扱う**（ギャランティ合算のデータソースは事前物販OS） |
| チケットの譲渡・リセール | **分配に対応**（複数枚購入のうち一部を第三者に譲渡可。全譲渡は不可）。**リセールは非対応**とし、キャンセル処理で対応 |
| 手数料モデル | 他劇団提供時のシステム利用料は**売上金額の5%** |
